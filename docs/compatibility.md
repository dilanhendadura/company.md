# Compatibility

Company.md provides portable company context and a tested CLI/skill installer. Compatibility belongs to the agent, its version, permissions, and available artifact tools; an IDE being able to open Markdown does not establish end-to-end support.

## Installed adapters

| Target | Project skill location | Verified here | Remaining host validation |
| --- | --- | --- | --- |
| `codex` | `.agents/skills/company` | Installer/runner; Codex CLI 0.153.0 explicit and implicit discovery, product switch, context receipts and storyboards | Initial named-product attempt required one retry; no PowerPoint editor test |
| `claude` | `.claude/skills/company` | Installer/runner; Claude Code 2.1.258 native skill discovery, product switch, context receipts and ambiguity | CLI harness permissions had to be corrected; no binary deck generated by this host |
| `cursor` | `.agents/skills/company` | Installer, bundled resources, runner against a real fixture, CLI validation | Run a clean Cursor session with discovery and artifact checks |
| `copilot` | `.agents/skills/company` | Installer, bundled resources, runner against a real fixture, CLI validation | Run a clean Copilot/VS Code session with discovery and artifact checks |

Install one target in an existing project:

```bash
companymd install ./project --agent codex
companymd install ./project --agent claude
```

Choose `cursor` or `copilot` instead of `codex` for those hosts. Codex, Cursor, and Copilot share the `.agents` location, so one installation serves all three. Reinstalling into an existing skill fails unless `--force` is explicitly passed; this prevents accidental replacement of local edits. The installer does not rewrite `AGENTS.md`, `CLAUDE.md`, company sources, or other agent configuration. Claude receives the same portable skill bundle in its native directory. Only reusable workflow instructions are distributed; company facts remain in the governed source pack.

The project paths above follow official documentation checked on 2026-09-06: [Codex skills](https://learn.chatgpt.com/docs/build-skills), [Claude Code skills](https://code.claude.com/docs/en/skills), [Cursor skills](https://cursor.com/docs/skills), and [VS Code Agent Skills](https://code.visualstudio.com/docs/agent-customization/agent-skills). These sources document discovery conventions, not certification of Company.md. Host trust, disabled skills, and nested-repository discovery settings can affect whether the skill loads.

The repository also packages the skill as a Codex plugin. The other targets above are project skill installations; no Claude, Cursor, or Copilot native plugin manifest is implied.

## Runtime and validation

The runner uses Node.js 20+ and selects an explicit `COMPANYMD_CLI` path, a workspace-local package/executable, an executable on `PATH`, or the pinned GitHub release. It resolves npm package entrypoints directly through Node, including Windows `.cmd` shims, so paths and arguments do not pass through a shell. Pin a compatible local installation for reproducible offline execution.

Routing, artifact bindings, and compact context require Company.md 0.4.0 or newer. The runner uses the trusted installed package's release metadata when compatible, avoiding an extra CLI process. Without compatible package metadata, it probes `--version` and rejects an old runtime before executing the task. A development checkout can use `COMPANYMD_CLI=<checkout>/dist/cli.js`; when its version has not yet been bumped, the runner additionally checks that `--help` advertises each requested feature. A skill pinned to an older release will not download that incompatible release for a new command. The package version, plugin version, and runner pin must be synchronized and the release must exist before distributing a new skill. No unreleased GitHub fallback is assumed available.

Reproduce adapter tests with:

```bash
npm run build
npx tsx --test test/install.test.ts test/runner.test.ts
```

These automated tests install each adapter in a temporary workspace, preserve existing instructions and company sources, then run its installed runner against a complete fixture. Runner tests also cover nested workspace discovery without an override, spaces in paths, literal shell metacharacters, old runtime rejection, development feature checks, and npm `.cmd` entrypoint resolution. The `.cmd` resolution test is portable; passing it on macOS does not establish a full Windows host session. Separate real Codex and Claude Code sessions supplied the host observations in the table. Two separate Codex desktop tasks also generated and rendered distinct five-slide product decks; this does not certify every editor or host. See [validation notes](validation-0.4.0.md) for scope and limits.

Before declaring an agent version end-to-end supported, run separate fresh sessions for explicit and implicit skill invocation. Test a named product, missing/ambiguous identity, missing design, a product switch in the same session, and two independent product decks. Record host/model versions, CLI version, selected sources, actual output, all slide renders, failures, and the artifact receipt. A renderer or presentation tool is required to complete a deck; the Company.md CLI only resolves and verifies its context and recorded evidence.

## Shared context contract

Use the installed skill, or add a thin routing instruction from [`integrations`](../integrations). Do not copy the whole pack into vendor instruction files.

1. Invoke `context` on the supplied workspace before recursively listing files. It discovers the registry or pack. Pass the company/product named by the user as `--subject`; a simple pack needs no registry, and its identity is validated too. Read resolved sources and bindings rather than inventorying historical fixtures or every installed skill.
2. Run one `companymd context` call with the narrowest sufficient profile and `--compact` for duplicate inherited prose. It validates before emitting context, so a separate `lint` call is only needed for diagnostics or CI.
3. For presentations, pass `--artifact presentation`, then load the explicitly bound design and template skill or file. Use the host's artifact capability to produce and inspect the deck.
4. Keep inherited prohibitions and clearance constraints. Use draft context only with user awareness; an authorized request to create and test a draft already supplies that awareness.
5. Generate a fresh context when the subject changes. Parent-company membership does not mix product facts, claims, or visual systems.
6. Bind the artifact receipt to the context receipt and verify it. Hash checks prove recorded source integrity; actual rendered inspection supports visual gates. Remote metadata verification is offline unless checked with the provider separately.

Registry and template details are in the skill's [product routing reference](../.agents/skills/company/references/product-routing.md). The root group, a subsidiary, and a product may each have their own pack. `parent` models membership; `extends` explicitly imports governed context, and artifact bindings select design/template sources.

## Other conventions

| Convention | Responsibility | Integration |
| --- | --- | --- |
| `AGENTS.md`, `CLAUDE.md`, native IDE instructions | Repository workflow and scoped agent instructions | Route to the skill or context command; retain existing project rules |
| `GEMINI.md` | Gemini project instructions | The checked-in thin adapter can route to the same contract; no tested installer target is claimed |
| `DESIGN.md` | Visual rationale, tokens, components, prohibitions | Link from a pack or explicitly bind it to an artifact in the registry |
| `llms.txt` | Public website discovery | Link a separately reviewed, sanitized public pack only when intentionally published |

Keep generated context temporary and source edits in the governed files. Publishing a public discovery index does not make internal, confidential, or restricted company context public.
